Ordinary questions and lexical candidates

An ordinary question is a request for relevant text expressed in everyday language. A retrieval system may normalize its terms, keep quoted phrases together, and match passages that contain those terms. That process can find useful context, but a lexical match does not prove that the passage answers the question. A passage can contain the requested words while describing a caveat, an unrelated example, or even the opposite of what the reader expected.

Keep question retrieval separate from an advanced Boolean query language. A query such as cache AND invalidation has operator syntax and a defined parsing rule. A natural question such as “How does a cache invalidation signal reach a reader?” should not be silently reinterpreted as that language. The interface should state which mode is active and never switch modes after an error.

Return the exact matched passage with its source title, requested URL, effective URL, matched terms or phrases, and an explicit retrieval status. If bounded work was skipped, report partial completeness. If no passage matched, say that no text matched. Do not label a negative query as answered or hide irrelevant hits with an invented confidence threshold.

Use an answer assessment of not_assessed when the system has not independently evaluated truth or entailment. Avoid answer snippets that were not present in the source and avoid confidence percentages that have no calibrated meaning. Honest limits help a reader decide whether to inspect more context or another source.

A question can name a code token such as resolve_evidence without changing retrieval mode. Query punctuation, including backticks around a code literal, should not silently turn an ordinary question into the advanced Boolean language.
